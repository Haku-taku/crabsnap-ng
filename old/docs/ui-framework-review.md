## 0. 审查结论

**结论：方向正确，但当前版本不可直接开工。有 3 个阻塞项、5 个高优缺口。**

| 等级 | 数量 | 含义 |
|---|---|---|
| **P0 阻塞** | 3 | 不解决就写第一行代码，会在第 2–4 周推倒重来 |
| **P1 高优** | 5 | 不阻塞开工，但相应子系统动工前必须补齐 |
| **P2 建议** | 4 | 可以在实现中按经验调整，但现在不写清会反复讨论 |

方向性判断（这些是对的，不需要改）：

- **结构持久 + 声明即时**的混合模型成立，且比纯即时模式更适合贴图工具（§0.1 的四个场景论证成立）；
- **不跑两遍布局**，用 `SizeClass` 四元组覆盖四种宽度需求，与 Qt/GTK 的实际做法一致；

- **渲染器参考 GPUI wgpu 的两阶段帧结构**，技术路线可行。

## P0-1：声明层无法表达"在自身周围绘制"

### 问题

§4.3 的 `Element` trait 有三个方法，但 §4.4 和 §3.4 的执行顺序把 `build` 放在**布局之前**：

```rust
fn build(&self, cx: &mut BuildCx<'_>) -> Decl;      // 阶段 ②，不知 rect
fn prepaint(&self, cx: &mut PrepaintCx<'_>, node: NodeRef<'_>) {}  // 融合趟回程，知 rect
fn paint(&self, cx: &mut PaintCx<'_>, node: NodeRef<'_>) {}        // 阶段 ⑤，知 rect
```

问题在于：**今天所有"围绕自身绘制"的效果（悬停光晕、焦点环、阴影、选中描边、贝塞尔控制柄）
都需要一个比自身 rect 更大的绘制区，而 `Decl` 里没有任何东西能声明这件事。**

调用方若在 `paint()` 里画到 rect 外，会撞上 §7 的 damage 计算（damage 按 rect 算）——
画出去的部分不进 damage，表现为"光晕边缘残留"。这不是理论问题：旧项目
`ui/chrome/mod.rs` 里专门有 `NODE_GRIP_LINE_WIDTH` 这类外扩常量，正是绕这个坑。

### 修复

`Decl` 增加**外扩声明**，让"绘制可能超出自身"成为布局期的合法信息：

```rust
pub struct Decl {
    pub key: Id,
    pub kind: NodeKind,
    pub props: Props,
    /// 绘制外扩：本节点可能画到 rect 外多远（阴影/光晕/控制柄）。
    /// Layout inflation: how far this node may paint outside its rect.
    pub ink_margin: Insets,
    pub children: SmallVec<[Decl; 8]>,
}
```

引擎据此：
1. damage 按 `rect + ink_margin` 计算（不是 rect）；
2. 父容器的裁剪区域相应放宽；
3. `ink_margin` 为 0 时零代价（绝大多数节点）。

**判据**：任何"看得见但点不到/擦不掉"的残留，追下去都会落到 `ink_margin` 漏声明。
加一条测试：`ink_margin=4` 的节点移动后，damage 覆盖 `old_rect+4 ∪ new_rect+4`。

## P0-2：`DrawList` 的构建者与 `Element::paint` 不匹配

### 问题

§6.2 说 `DrawList` 是"每帧重建、无保留状态的命令列表"，§8.4 说效果的源是
"`DrawList` 中它**之前**、同层或更低层、与 `rect` 相交的图元"。

这两条合起来要求：**绘制必须按严格画家顺序、在一个线性流里发生**。
但 §3.4 的执行顺序是"paint 阶段按树前序遍历，每个节点调自己的 `paint()`"——
如果某个控件想"先画背景、再画子内容、最后画前景"，它必须在**自己的 `paint()` 里**
驱动子节点的绘制，否则前景会被后序节点的命令挤到前面。

而当前设计里子节点是**引擎递归调用**的，控件拿不到"在我的中间插一句"的能力。
结果是：**任何需要前景装饰的容器（工具栏的滚动条、菜单的高光、聚焦容器的焦点环）
都画不正确。**

### 修复

`PaintCx` 提供显式的绘制分段：

```rust
pub trait Element {
    fn paint(&self, cx: &mut PaintCx<'_>, node: NodeRef<'_>) {
        self.paint_background(cx, node);
        cx.paint_children(node);          // 引擎在此插入子节点命令
        self.paint_foreground(cx, node);
    }
    fn paint_background(&self, _: &mut PaintCx<'_>, _: NodeRef<'_>) {}
    fn paint_foreground(&self, _: &mut PaintCx<'_>, _: NodeRef<'_>) {}
}
```

默认实现就是"背景 → 子节点 → 前景"，与画家顺序一致；
`cx.paint_children` 只能调用一次（`debug_assert`），防止子节点被画两遍。

**同时补一条不变量**：`DrawList` 的命令顺序 = **树的后序**（子先于父的前景），
这一条要写进 §6.2，因为它是效果源语义的前提。

## P0-3：效果源扫描的复杂度是 O(n²)

### 问题

§8.4 定义效果源为"命令流中在它之前且与 `rect` 相交的图元"。朴素实现是每个效果
扫一遍之前的全部命令——`m` 个效果 × `n` 条命令。

真实的工具栏：约 200 条图元、3 个效果面（工具栏毛玻璃、菜单毛玻璃、调试浮层）。
4800 次矩形相交判断/帧，看起来能接受，**但这不是上限**：贴图编辑态每帧重建内容层，
命令数会随标注数量线性增长，而效果面数量也随面板数增长。

更麻烦的是**级联**：§8.6 说"把上一条效果刚算过的区域追加进下一条的 source_dirty"，
这条链本身是线性的，但与"源扫描"叠加后就变成每个效果都要重扫。

### 修复

在 `DrawList` 构建时维护一份**空间索引**：

```rust
pub struct DrawList {
    cmds: Vec<Cmd>,
    /// 命令 → 矩形 的空间分桶（16×16 格），供效果源查询用。
    /// Spatial buckets for effect-source queries.
    grid: HashMap<(i32, i32), SmallVec<[u32; 2]>>,
    /// 每个效果的源查询结果（构建时增量累积，不在解算阶段重扫）。
    /// Per-effect source cmd ranges, accumulated while building.
    sources: Vec<SourceRange>,
}
```

效果节点在**被追加进命令流的那一刻**，就能确定自己的源（此前所有命令中与它相交的那些），
之后解算阶段直接读 `SourceRange`。复杂度从 O(m·n) 降到 O(n·log n)。

**这不是优化，是可行性问题**：如果源扫描是 O(n²)，"贴图 + 标注 + 多个效果面"这个
我们最核心的场景会在第一版就卡住。**必须在实现前定下数据结构**，事后加索引要改公共类型。

## P1-1：事件处理器与 `&mut AppState` 的所有权模型未定义

§4.1 的例子是 `.on_click(move |cx, _| cx.action(UiAction::SelectTool(tool)))`，
§5.5 的派发是"沿路径调 `handler(n, phase)`"。但**从没说处理器存在哪里、谁拥有它**。

三种可能，各有代价：

| 方案 | 代价 |
|---|---|
| 处理器存在 `Node` 里（`Box<dyn FnMut>`） | 每帧重建 → 每帧堆分配；`'static` 闭包捕获不了 `&AppState` |
| 处理器**不存**，只在事件发生时由 `Decl` 里的 `NodeKind` 查表 | 灵活度低，但零分配、无生命周期问题 |
| 处理器存引擎外部（`&mut dyn Handler`） | 需要把所有状态塞进一个 trait 对象 |

**建议**：**动作即数据，不是闭包**。`.on_click(Action::SelectTool(tool))`，
引擎只派发 `Action`，由主 crate 在一个 `match` 里处理。
理由可推导：闭包捕获 `&mut AppState` 会让 `retained tree` 与 `AppState` 的借用重叠，
这是 GPUI 被迫引入 `Entity` + `Rc<RefCell>` 的根因（§1.2 已列为"不抄"）。
用动作数据则天然没有借用问题，且动作本身可序列化（便于测试与诊断）。

这条**必须在开工前定**，因为它决定了 `ui-el` 的 API 形状。

## P1-2：文本测量与布局增量的交互未定义

§5.2 说"文本测量走 `TextMeasure` trait，按 `(text, style, max_width)` 缓存"，
§5.2.3 说"高度依赖宽度"。但**增量布局**（§5.2.5）只说了"dirty 节点重算"，
没说文本节点在**宽度变化但文字未变**时如何失效。

问题：宽度变化 → 折行结果变 → 高度变 → 父容器高度变 → 连锁。这是布局里唯一的
"下游依赖上游"关系，§5.2.3 说"单向，所以不需要第二趟"——**这个结论只在单次布局内成立，
跨帧的增量复用不成立**：如果缓存的 `max_width` 与本次约束不同，必须重测。

**建议**：把文本节点的缓存键改成 `(text_hash, style_hash, max_width_rounded)`，
并在 `Node` 上记录"上次测量用了什么约束"。宽约束变了 → 视为 dirty。这一条要写进
§5.2.5 的 dirty 来源列表，否则会表现为"窗口缩放后文字不重排"。

## P1-3：`PushLayer` 与效果面的交互未定义

§12.6 定义 `PushLayer` 为"先渲染到离屏目标再整体混合"，§8.4 说效果源是"之前的图元"。

**问题**：`PushLayer` 内部的效果面，源应该只包含层内图元，还是层外的也算？
两种都有正当用途：

- 只算层内 → 菜单内部的毛玻璃只糊菜单自己的背景（不现实，菜单背景通常透明）；
- 层外也算 → 需要把"层之前的合成结果"作为源（可行，但要求 layer pass 开始前先拍快照）。

**建议**：明确规定 **效果的源 = 到该命令为止、已合成到当前目标上的全部像素**，
`PushLayer` 内部的效果因此能看到层外内容（因为它读的是"当前目标"而不是"当前层的命令列表"）。
这条同时解释了为什么 effect 的 `capture` 动作是从目标拷块——它天然包含层外内容。

**代价**：`PushLayer` 内的效果会让"层必须先物化"（不能延迟到合成时算）。
在 CPU 后端上这是自然行为；在 GPU 上意味着 layer pass 必须串行于效果 pass。
需要写进 §12.1 的 pass 顺序图，否则实现时会出现"效果在 layer pass 之前执行"的错误。

## P1-4：焦点与键盘的表单级语义（Tab 顺序、快捷键冲突）未覆盖

§5.6 定义了焦点路径 + Tab 前序，但没有定义：

1. **Tab 分组边界**（工具栏内 Tab 是否跳出到下一个面板）；
2. **快捷键与文本输入的冲突仲裁**（`Ctrl+A` 在文本框里是"全选"，在画布上是"全选标注"）；
3. **模态期间焦点约束**（菜单打开时 Tab 是否能在菜单外的控件间移动）。

这三条在贴图工具里都会遇到。建议补一张**输入优先级表**：

```text
按键事件优先级（从高到低）：
  1. IME 组字中 → IME（不派发给控件）
  2. 焦点节点是文本输入 → 文本编辑（Ctrl+A/C/V 归它）
  3. 焦点路径上的 Bubble 处理器
  4. 全局动作表（actions crate）
```

## P1-5：`Damage` 与"效果输出变化"的循环依赖风险

§7 列的四个 damage 来源里，第 4 条是"效果级联：效果面重算区域"。但效果的 source
本身来自 damage（§8.6 的 `A = (damage ± pad) ∩ old ∩ new`）。**这是一个循环**：

```text
damage → 效果重算区 → 效果输出变 → 新 damage ...
```

当前文档没有说清迭代几次。**建议明确**：效果 **不产生新 damage**——效果只在
"它所占据的矩形内"改变像素，而那个矩形已经在 damage 里（因为效果的输入变了）。
所以 damage 的计算顺序必须是：

```text
① 收集 基础 damage（布局/绘制/动画）
② 用 ① 解算效果（只读 ①，不写回）
③ damage 与 效果重算区取并集，作为最终提交范围
```

这需要一个明确的"damage 两阶段"表述。否则实现时很容易写成"效果算完再追加 damage"，
导致同一帧内 damage 越滚越大（永不收敛）。

## P2-2：`SizeClass` 的 `shrink` 语义不够用

`shrink: bool` 只能表达"能压到 hint 以下"，但压到哪没定义。Qt 的做法是
`minimumSize` 提供下限——我们的 `min` 就是下限，所以 `shrink` 是多余的：
**能压 = `min < hint`**。建议删掉 `shrink` 字段，减少一个可能不一致的状态。

## 附：审查方法

本次审查没有逐行校对，而是沿四条路径推演：

1. **写一个真实控件**（工具栏按钮 + 悬停光晕 + 焦点环）→ 撞出 P0-1；
2. **写一个真实容器**（带滚动条的工具栏）→ 撞出 P0-2；
3. **估算最坏场景的复杂度**（贴图 + 200 条标注 + 3 个效果面）→ 撞出 P0-3；
4. **检查每条"不变量"在增量路径上是否仍成立**（文本测量、damage 与效果）
   → 撞出 P1-2、P1-5。

建议后续每次大改设计后都用这四条路径重做一遍，代价约一小时，能提前发现同类问题。
