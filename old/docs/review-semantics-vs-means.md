# 审查：语义与手段的绑定问题

> 范围：像素后端效果（§8）与采样引擎（§6.4）
> 方法：按"**哪部分是必须正确的语义、哪部分是可替换的实现手段**"逐项检查。
> 触发：上一轮"HDR 存储域 vs 运算域"的纠错暴露了这个模式——把必须正确的语义与实现它的
> 具体手段绑死，代价是过早失去替换空间。
> 所有数值为本机脚本计算（可复现，见各节代码）。

---

## 0. 结论

**找到 3 处同类错误、2 处定义缺口、1 处被忽略的正确性问题。**

| # | 位置 | 问题 | 等级 |
|---|---|---|---|
| A1 | `PixelBackdrop.pad` / `grid` | **把"某算法当前实现的半径"当成引擎语义**，冻结了实现选择 | 高 |
| A2 | `PixelBackdrop.extends` | 同上——边缘策略是算法的实现细节，不该进引擎元数据 | 中 |
| A3 | `Sampling` 缓存键 | **缓存键绑定了"尺寸 + 采样方式"，但没绑定色彩域**，HDR 下会命中错误缓存 | **高** |
| A4 | §8.6 级联 | `pad` 逐级**相加**这条算术没写出来（已实测确认是相加） | 中 |
| A5 | §6.4.2 | "CPU 与 GPU 必须数值一致"——**这条不成立**，与 AA 的结论矛盾 | 中 |

其中 **A3 是真正的 bug**：HDR 需求加进来后，同一份内容在不同色彩域下的重采样结果不同，
而缓存键里没有色彩域。

## A1：`pad` 把实现细节冻结成了引擎语义

### 问题

```rust
pub struct PixelBackdrop {
    /// 高斯 = ⌈3σ⌉，马赛克 = 块大小，液态玻璃 = 折射位移上限。
    pub pad: u32,
}
```

`pad` 本身是**必要的引擎语义**（引擎要用它算 damage 外扩与级联传播，见 A4）。
问题在于**谁来计算它**：现在是"算法自己算好一个数交上来"。

于是：**`3σ` 这个系数被冻结进了 API 契约**。
如果将来改用"5σ 截断"或"按能量集中度自适应"，`pad` 会变大，**所有依赖它的 damage 计算
都会变化**——而这些变化发生在引擎之外，引擎无从校验。

更糟的是：`⌈3σ⌉` 是**当前 CPU 实现的选择**，不是"高斯模糊"这个效果的语义。
高斯模糊的语义是"支撑集为无穷（理论上）"；`3σ` 是**可接受的近似**。

### 这是同一类错误

| | 必须正确的语义 | 可替换的手段 |
|---|---|---|
| HDR（上一轮） | 运算在线性光域 | f16 缓冲 / LUT 往返 |
| **效果半径** | **输出在 p 处依赖源 p±R 对某个 R 成立** | **R = 3σ / 5σ / 自适应** |

### 修法：把"保证"与"估计"分开

```rust
pub struct EffectReach {
    /// 算法**保证**的影响半径：引擎据此外扩 damage，超出即为错误。
    /// Guaranteed support radius; anything beyond it is a bug, not a rounding choice.
    pub guaranteed: u32,
    /// 算法**实际**用到的半径（可能小于保证值，用于避免过度重算）。
    /// Actual radius used; may be smaller than `guaranteed`.
    pub actual: u32,
}
```

引擎只用 `guaranteed` 决定**正确性**（damage 必须覆盖它），用 `actual` 决定**效率**
（少算一些）。两者分离后：

- 换 `3σ → 5σ` 只需改算法实现，`guaranteed` 变大自然正确，引擎代码不动；
- 引擎可以 `debug_assert!(actual <= guaranteed)`，把"算法算错了"变成可检测的。

**并且必须有一条测试**：对每个注册的效果，用脉冲输入实测"影响半径 ≤ guaranteed"。
这是 A1 的验收判据，也是唯一能让 `guaranteed` 可信的方式。

## A2：`extends`（边缘策略）不该进引擎元数据

### 问题

```rust
/// 边缘策略：pad 超出源范围时怎么取值（Clamp / Transparent / Reflect）。
pub extends: EdgeMode,
```

引擎拿它做什么？**什么都不做**——它只在算法的卷积实现里用到。
它出现在 `PixelBackdrop` 里，违反了 §8.3 的"三个正交点"原则：
引擎说自己"只知道数字，不知道怎么算"，但 `extends` 是一个**算法参数**混进了引擎元数据。

### 但这背后有个真问题

如果 `extends` 是算法自由选择的，那么**同一个效果在画布边缘与内部的行为不同**：
- `Clamp`：边缘像素被重复，模糊后边缘变亮/变暗；
- `Transparent`：边缘渐隐，看起来像"内容到边就没了"。

对一个全屏覆盖层，`Clamp` 是错的（边缘会出现从屏幕外拉进来的假色）；
对一张贴图，`Clamp` 是对的（内容在边缘之外确实"延续"）。

**所以真正的语义是：边缘行为应由"内容边界"决定，而不是由算法决定。**

### 修法

引擎元数据里删掉 `extends`，改为在**源描述**里声明：

```rust
pub struct EffectSource {
    /// 源的边界内是有效内容，边界外按此策略扩展。
    /// Inside `bounds` is valid content; outside extends per this policy.
    pub bounds: Rect,
    pub outside: EdgeMode,   // 由"这是贴图还是屏幕覆盖层"决定，不是算法决定
}
```

算法读它（卷积时用），引擎只负责**把它设对**（根据 canvas/屏幕语义）。

## A3【真 bug】：采样缓存键缺色彩域

### 问题

```rust
// 引擎按 (CanvasId, generation, display_size, visible_region, Sampling) 缓存
```

HDR 需求加入后，**同一份内容在不同色彩域下的重采样结果不同**：

- 在 `LinearF16` 域线性插值 = 正确的亮度插值；
- 在 `Srgb8` 域线性插值 = 编码域插值，暗部偏暗（§5.3.2 实测：黑白棋盘差 61/255）。

若缓存键不含域，则**先渲染到 SDR 的缓存会被 HDR 路径命中**（或反之），
表现为"切到 HDR 后边缘偏暗/偏亮，且只在被缓存过的区域出现"——**极难定位的一类 bug**。

### 还有一个更隐蔽的

`Sampling::Nearest` 在**放大**时两域等价（逐像素复制，无运算）；
但在**缩小**时 `Nearest` 会抽样——而抽样点在两域的物理意义相同（坐标），
所以 `Nearest` 确实域无关。**但 `Linear` 不是。**

### 修法

```rust
pub struct SampleKey {
    canvas: CanvasId,
    generation: u32,
    display_size: (u32, u32),
    visible: Region,
    sampling: Sampling,
    /// 运算域：决定插值在哪个空间做。
    /// Operation domain: which space the interpolation happens in.
    domain: StorageDomain,     // ← 新增
}
```

并且明确一条规则：**`Linear` 采样必须在线性光域做**，即使目标是 `Srgb8`。
这与 §5.3.3 的处理一致（LUT 往返）。`Nearest` 可以跳过线性化（省一次查表）。

## A4：级联的 `pad` 算术没写出来

### 现状

§8.6 只说"把上一条效果刚算过的区域追加进下一条的 `source_dirty`"。**没说是加还是取 max。**

### 实测

两级 box blur 串联，一维脉冲输入：

| `pad1` | `pad2` | 实际传播半径 | `pad1+pad2` | `max` |
|---|---|---|---|---|
| 1 | 1 | 2 | 2 ✓ | 1 ✗ |
| 2 | 3 | 5 | 5 ✓ | 3 ✗ |
| 5 | 5 | 10 | 10 ✓ | 5 ✗ |
| 10 | 4 | 14 | 14 ✓ | 10 ✗ |

**结论：是相加。** 并且进一步验证了"damage ± (pad1+pad2) 的保守估计是否覆盖实际"：

```text
E1 输出真实变化范围: 146..154（宽 9）
E2 输出真实变化范围: 140..160（宽 21）
保守估计 damage ± (pad1+pad2): 140..160  ← 恰好覆盖
```

### 修法

写进 §8.6：

```text
第 k 个效果的累计半径 R_k = Σ pad_guaranteed(0..k)
它对 damage 的重算区 = damage ± R_k
```

这样级联是一次线性累加，不需要逐级"追加 source_dirty"这种模糊说法。

## A5："CPU 与 GPU 必须数值一致"与本设计矛盾

### 问题

§6.4.2 写：

> **CPU 与 GPU 必须数值一致**：`Nearest` 的取样几何是...`Linear` 的权重同样钉死。
> 这一条由"同一张 2×2 棋盘图缩放到 1.5×，两个后端逐像素比对"的锚定测试保证。

而 §12.4（抗锯齿）刚刚论证过：**两条后端的 AA 机制不同（超采样 vs 距离场），
边缘像素天然差 1–3/255，不能要求逐像素相等。**

这两条**互相矛盾**：如果采样要求逐像素相等，为什么 AA 不要求？

### 为什么这条本身也不成立

`Linear` 采样在不同后端上：
- CPU：`lerp(a, b, t)`，`t` 由整数算术算出；
- GPU：`texture(sampler, uv)`，`t` 由硬件的定点插值算出。

**两者在边界上有微小差异**（GPU 的采样点位置通常是像素中心 +0.5，且精度有舍入）。
要求"逐像素相等"会让这条测试永远红。

### 修法

统一标准：**采样也用不变量约束，不用逐像素相等。**

| 不变量 | 测法 |
|---|---|
| **最近邻是恒等** | `Nearest` 在 1:1 时逐像素等于源（这个是真的能相等） |
| **线性是凸组合** | 任意点的结果落在两邻点的 [min, max] 内（无过冲） |
| **线性可复现** | 同一后端重复采样结果完全相同（确定性） |
| **位置误差** | 50% 等值线位置差 < 0.5px（CPU vs GPU） |

这与 `dual-backend.md` §2.2 的 AA 不变量是同一套哲学，避免了双重标准。

## A6：`grid` 的语义歧义

```rust
/// 位置格：源网格锚点。马赛克 = 块大小（平移非整数块就要整块重算），其余 = 0。
pub grid: u32,
```

`grid = 0` 表示什么？两种读法：

1. **没有网格约束**（可以亚像素平移，任意复用）；
2. **网格 = 1 像素**（任意平移都是整数像素，总能复用）。

两者在整数像素平移下等价，但在**亚像素平移**（`rect` 是 f32）下不同：
读法 1 允许复用；读法 2 要求平移量是整数像素，否则重算。

**建议明确读法 1，并改名为 `requires_aligned_translation: Option<u32>`**：
`None` = 无约束，`Some(block)` = 必须整块对齐。语义比 `0` 这个"魔法值"清楚。

## 一个可复用的检查方法

这次审查用的判据可以固化成 review 时的清单：

> 对设计里每一个字段/参数，问两句：
> 1. **引擎需要读它来做正确性决策吗？** 不需要 → 它不属于引擎元数据（A2、E2 的 `extends`）。
> 2. **它是"保证"还是"当前实现的选择"？** 是后者 → 必须与保证分离，否则实现一变就破契约（A1、HDR 的 f16）。
>
> 对每一条"必须相等"的断言，问：**两个实现机制不同时，这条还能成立吗？**
> 不能 → 换成不变量（A5、AA）。
