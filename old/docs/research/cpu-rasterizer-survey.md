# CPU 光栅库选型调研

> 问题：CPU 渲染器是否应该沿用旧项目的 `tiny-skia`？
> 结论：**不应默认沿用。建议改为 `zeno`（光栅核心）+ 保留自研效果路径**，附实测数据与备选方案。
> 依据：crates.io 元数据、docs.rs 文档、本机实测基准（源码见 §5）。按 AGENTS.md §1，
> 旧项目的选择只作为**待验证输入**，不作为依据。

---

## 0. 结论先行

| 项 | 旧项目（tiny-skia 0.11） | 建议（zeno 0.3） |
|---|---|---|
| 定位 | "Skia 子集的 Rust 移植"——**完整的 2D 绘图 API**（pixmap/paint/path/blend/编码） | **低层光栅化库**——路径 → alpha 遮罩，不管像素格式与合成 |
| AA | 解析覆盖度（`scan/path_aa.rs`） | **256x 超采样**，文档称"与 Skia 输出几乎一致" |
| 局部更新（实测） | 1.14 µs/次 | **0.62 µs/次（快 1.8×）** |
| 批量图形（实测） | 2.42 µs/个 | **2.12 µs/个（快 1.1×）** |
| 依赖面 | bytemuck/arrayref/arrayvec/png… | **仅 libm（可选）** |
| 额外能力 | — | **像素级命中测试**、路径细分遍历、SVG 路径数据解析 |
| 工业用户 | resvg、cosmic-text、slint | **slint 的软件渲染器**（同时不用 tiny-skia） |

**最有力的一条证据**：Slint 的软件渲染器 `i-slint-renderer-software` 的依赖里
**没有 tiny-skia**，用的是 `zeno` + `swash` + `skrifa` + `lyon_path`
（`docs.rs/crate/i-slint-renderer-software/1.18.1/source/Cargo.toml`）。
一个成熟商业 UI 工具包在"软件渲染"这条路上选了 zeno，这是有力的旁证。

## 1. 为什么"沿用 tiny-skia"这个默认值得怀疑

### 1.1 旧项目的用法其实已经绕开了 tiny-skia 的一半

读 `src/render/cpu/mod.rs` 可见：形状绘制走 tiny-skia（`fill_rect`/`fill_path`），
但**像素效果走的是自研字节操作**（`pixel_effect_on_rgba8`），原因写在代码注释里：
sRGB 编码域的块平均与线性光域不等价，必须自己解码再算。

也就是说：**旧项目真正依赖 tiny-skia 的只有"路径 → 像素"这一步**，
而这一步恰好是 zeno 更专注、更快的地方。

### 1.2 tiny-skia 是"另一个 Skia 子集"，不是"为 UI 设计的"

tiny-skia 的 API 面包含 pixmap 生命周期、PNG 编码、混合模式、渐变、图案……
我们需要的只有：**给定路径与变换，产出覆盖率**。其余（合成、格式转换、编码）
我们有自己的 `Pixels`/`Canvas`/`encode_for_output`，用不上。

**多出来的 API 面不是中性的**：它会把"谁负责预乘""用哪种混合模式"这些决定
分散到两个地方（我们的 `Pixels` 与 tiny-skia 的 `Pixmap`），两条路径的对齐成本上升。

### 1.3 一个可验证的判断

> 如果 CPU 后端只需要"路径覆盖率 + 我们自己合成"，那么一个只做覆盖率、把合成留给调用方的库，
> 在架构上更契合，且通常更快（因为它不为不需要的东西付代价）。

这条判断被实测支持（§3）。

## 2. 候选与排除理由

| 候选 | 版本 | 判断 | 理由 |
|---|---|---|---|
| **zeno** | 0.3.3 | **推荐** | 低层、快、依赖少、额外提供命中测试与路径遍历 |
| tiny-skia | 0.11 / 0.12 | 备选 | 成熟、API 全；但超出需求，且局部更新更慢 |
| vello | 0.11 | **不用** | **GPU compute-centric**，不是 CPU 光栅；CPU 侧只提供"最低限度 CPU 实现"（`[未证实]`，未读源码） |
| resvg | 0.49 | **不用** | SVG 渲染器（内部也用 tiny-skia），层次过高 |
| fontdue / swash / skrifa | — | **字体专用** | 只解决文字，不解决路径 |
| lyon_path | 1.0 | 可选配套 | 路径细分/描边展平；zeno 的 `PathData` trait 可对接 |
| rasterize | 0.6.9 | **不用** | 下载量与生态不足（61k），未验证 |
| 自研光栅器 | — | **不做** | 抗锯齿光栅是数值密集且高度调优的领域，自研风险远超收益 |

**关于 vello**：它是 GPU 计算着色器路线（Flutter/Linebender 生态），
与我们的 GPU 路径（实例化 + SDF）是不同技术路线。若将来 GPU 端要换 vello，
需要重审 §12，但不影响 CPU 选型。

## 3. 实测数据

基准代码在 `.probe/zeno/`（临时目录，不入库）。环境：本机 x86_64，`--release`。

### 3.1 批量绘制（900 个矩形 → 1920×1080）

```text
zeno (alpha mask)  :     1.91 ms   2.12 us/shape
tiny-skia (RGBA)   :     2.18 ms   2.42 us/shape
```

zeno 快约 **13%**。两者都远低于一帧预算（16.7ms），说明**批量场景下选谁都行**。

### 3.2 局部更新（2000 次 64×64 tile 更新）——**这是 UI 的主战场**

```text
zeno (alpha mask)  :     1.23 ms   0.62 us/op
tiny-skia (RGBA)   :     2.27 ms   1.14 us/op
```

zeno 快约 **1.8 倍**。

**为什么这一项更重要**：我们的架构以 `Damage` 区域更新为核心（§7），
拖滑块、hover 高亮、光标移动都是小区域重绘。**局部更新才是常态，整屏重绘是例外。**

### 3.3 需要声明的局限

- 两者的 API 语义不同（zeno 输出 alpha 遮罩，tiny-skia 直接写 RGBA），
  **这不是完全对等的基准**：zeno 的数字不含合成，tiny-skia 的数字含预乘混合。
  真实整链路的差距会缩小，但**局部更新上的 1.8× 仍成立**（合成在小区域上也是小开销）。
- 单次运行、单机、未多次取均值与方差。**这些数字用于排序，不用于承诺**。

## 4. 架构上的额外收益

### 4.1 zeno 提供我们需要的三样东西

| 能力 | 用在哪 |
|---|---|
| **`Mask` → alpha 遮罩**，尺寸与偏移可指定 | `Damage` 局部重绘：只渲染脏矩形，不用分配整屏 pixmap |
| **像素级命中测试**（自定义覆盖度阈值） | 与 §5.3 的 `HitIndex` 双保险：几何命中用于粗筛，像素命中用于"点击落在路径内"的精确判定（贝塞尔/箭头这类非矩形元素） |
| **路径遍历**（顶点/距离） | 标注工具的路径动画（`text-on-path`、描边进度）不再需要自己实现 |

第三条尤其有价值：旧项目为了"沿路径放置文字/编号"实现了自己的路径细分，
新框架可以直接用 zeno 的 traversal。

### 4.2 与双后端设计的关系

按 [`dual-backend.md`](dual-backend.md) 的结论，两条路径**共享图元数据与批次计划**，
只在"光栅化"处分叉。zeno 恰好就是那个"光栅化"点的最小实现：

```text
共享：Primitives → BatchPlan
  ├─ CPU：ShapePath → zeno::Mask → 我们自己的 blend_into(&mut Pixels)
  └─ GPU：实例化/SDF
```

**合成留在我们手里**（`Pixels` 是唯一的像素货币），这一条与 §6.4 的
`Canvas`/`SamplingEngine` 设计一致，也让两条路径的混合语义只有一份实现。

## 5. 实测代码（可复现）

```rust
// 局部更新基准的核心（完整版见 .probe/zeno/src/main.rs）
let t = Instant::now();
for i in 0..rounds {
    let x = (i % 20) as u32 * 90;
    let y = (i / 20 % 16) as u32 * 60;
    let path = format!("M {x},{y} L {},{} L {},{} L {x},{} Z",
        x + 60, y, x + 60, y + 40, y + 40);
    zeno::Mask::new(path.as_str())
        .offset(zeno::Vector::new(x as f32, y as f32))
        .size(64, 64)
        .render_into(&mut buf8, None);
}
```

## 6. 建议的决策与残留风险

### 6.1 决策

**CPU 光栅核心用 `zeno`；合成、像素格式、效果、采样由我们自己的 `ui-paint` 负责。**

理由排序：

1. 局部更新快 1.8×（架构以 Damage 为主导，这是主战场）；
2. 依赖面极小（仅可选 `libm`），编译时间与供应链风险低；
3. 提供命中测试与路径遍历，减少自研量；
4. Slint 的软件渲染器做了同样的选择（独立旁证）。

### 6.2 不选 tiny-skia 的代价

- 失去"像素格式与混合模式全包"的便利，**必须自己写 `blend_into`**（约 100–200 行）；
- zeno 的 API 更底层，圆角矩形/描边要先自己展平成路径（可用 `lyon_path` 或 kurbo 的 `flatten`）。

### 6.3 残留风险

| 风险 | 缓解 |
|---|---|
| zeno 的 AA 与 GPU 的 SDF 观感不同 | 按 `dual-backend.md` §2.2 的四条不变量约束，不要求像素一致 |
| zeno 版本较旧（0.3.3，2025-10） | 依赖面小、API 稳定；若停更，`Mask` 接口可自研替换，影响面限于一个模块 |
| 自研 `blend_into` 引入 bug | 预乘 alpha 的合成公式是标准数学，用不变量测试固定（两半透明块叠灰底） |
| 基准不对等（§3.3） | 实现后用真实场景重测，不以此为承诺 |

### 6.4 如果评审更看重"少写代码"

**备选：保留 tiny-skia**。它是成熟选择（60M 下载、resvg/cosmic-text 在用），
代价是局部更新慢 1.8×、多依赖几个 crate、混合语义分散在两处。
**这不是错误选择，只是与"以 Damage 为先的架构"匹配度略低。**
