# 双渲染路径（CPU / GPU）可行性设计

> 问题：能否设计一套结合各 UI 框架特点、**同时支持 CPU 与 GPU 渲染、且两条路径都有良好性能**的框架？
> 结论：**可以，但必须选对共享边界**。本文给出这个边界，以及为什么另一种切法会失败。
> 证据：tiny-skia 0.11.4 源码（本机）、GPUI / egui 源码（本机）；未核对的部分标 `[未证实]`。

---

## 0. 结论

**可以。关键是把"共享什么"选在图元语义层，而不是在光栅结果层。**

| 层 | 是否两条路径共享 | 说明 |
|---|---|---|
| 声明 / 树 / 布局 / 命中 / 事件 / 动画 / 脏区 | **完全共享** | 纯逻辑，与渲染无关 |
| 图元生成（`Primitives`）、批次计划（`BatchPlan`） | **完全共享** | 决定"画什么、按什么顺序" |
| **AA 覆盖度** | **必须不共享**（见 §2） | CPU 用解析覆盖度，GPU 用 SDF/羽化 |
| 像素处理原语（模糊/马赛克核） | **语义共享，实现各自** | 同一套参数 → 同一视觉结果 |
| 呈现（present） | 完全共享 | `PresentTarget` 抽象 |

**"两条路径都性能良好"的前提是承认它们擅长的事不同**：

- CPU 路径擅长：小面积更新、无 GPU 设备、确定性输出、离线导出。
- GPU 路径擅长：大面积重绘、大量图元、效果链、高分辨率。

**所以不是"两条路一样快"，而是"每条路在它该快的场景里快"。** 见 §4 的性能预算分配。

---

## 1. 三个必须共享的东西（共享得越多，两条路越不会漂移）

### 1.1 图元数据（`Primitives`）

两条路径吃**同一份** `RectPrim`/`PathPrim`/`GlyphPrim`/`CanvasPrim`。这是最重要的共享点：
**任何"画什么"的改动只写一次**。

### 1.2 批次计划（`BatchPlan`）

`BatchPlan` 决定渲染顺序、裁剪段、层边界。两条路径都按它遍历——
**顺序错误（z-order、clip 泄漏）只会在同一个地方发生一次**。

### 1.3 不变量测试（最重要）

```rust
#[test]
fn cpu_and_gpu_produce_the_same_picture_for_primitive_shapes() { .. }
```

对同一组图元（纯色矩形、圆角矩形、描边路径、文字），两条路径渲染到同尺寸目标后
**逐像素比对**，允许容差（见 §3.2 的容差表）。

**这条测试是整个设计的地基**：没有它，两条路径会在几个月内悄悄分叉
（egui 和 GPUI 都没有第二套后端要维护，所以它们没有这个问题；我们有）。

---

## 2. 必须分开的：抗锯齿（这是最容易做错的地方）

### 2.1 两条路径的 AA 机制本质不同（已核实源码）

| | tiny-skia（CPU） | GPU（我们选 SDF/羽化） |
|---|---|---|
| 机制 | **解析计算每像素被路径覆盖的面积** | 距离场或几何羽化，按距离算 alpha |
| 证据 | `scan/path_aa.rs:270-284` 的 `coverage_to_partial_alpha`；`scan/hairline_aa` | egui `tessellator.rs:796-810`（羽化）；GPUI `fs_quad` 的 SDF |
| 适用 | 任意路径、任意曲线 | 规整形状（圆角盒）、可行瓦化的描边 |

**结论：不要试图让两者输出完全相同的 alpha 值。** 解析覆盖度与距离场近似在
**边缘像素上会差 1–3/255**，这是数学差异，不是 bug。

### 2.2 由此得出的规则

> **AA 是"实现定义"的：每个后端可以有不同的边缘像素，但不变量是"覆盖度单调且能量守恒"。**

可测的不变量（替代"逐像素相等"）：

| 不变量 | 测法 |
|---|---|
| **面积守恒** | 一个 100×100 的不透明矩形，两条路径渲染后的 alpha 总和相差 < 0.5% |
| **边缘单调** | 斜边上的 alpha 沿法线单调递增（无极值振荡） |
| **无溢出** | 半透明层叠加不出现 > 255 或负值 |
| **形状位置** | 边界位置误差 < 0.5px（比较 50% alpha 等值线） |

**这四条比"逐像素相等"更可执行**，也更能抓住真问题（溢出、振荡、位置漂移），
而不会因为 AA 机制不同就一直红。

### 2.3 如果坚持两条路完全一致

那就只有一条路：**CPU 三角化 + 羽化，GPU 吃同一份三角形**（egui 的做法）。
代价：

- GPU 端失去 SDF 与实例化的全部收益（无法 `draw(0..4, instances)`，必须上传顶点）；
- 每次缩放变化要重新三角化；
- CPU 端必须自己实现羽化（tiny-skia 的解析覆盖度用不上，得旁路它）。

**这是一个真实可选方案**，如果"两条路完全一致"的优先级高于"GPU 性能"，
应该选它。默认建议**不选**：我们 GPU 要跑 4K 全屏覆盖层 + 效果链，实例化收益太大。

## 3. 共享边界的精确划分

```text
┌─────────────────────── 两条路径共享 ────────────────────────┐
│ 树 / 布局 / 命中 / 事件 / 动画 / Damage                      │
│ Primitives（类型化图元数据）                                  │
│ BatchPlan（顺序、clip 段、层边界）                            │
│ ClipStack / LayerStack 语义                                  │
│ 采样意图（Sampling::Nearest/Linear）+ 采样几何规则            │
│ 效果参数（pad / grid / extends / 程序参数）                   │
│ PresentTarget 接口                                           │
└──────────────────────────────────────────────────────────────┘
                              │
        ┌─────────────────────┴─────────────────────┐
        ▼                                           ▼
┌─────────────────────┐                   ┌─────────────────────┐
│ CPU 后端            │                   │ GPU 后端            │
│ tiny-skia 光栅      │                   │ 实例缓冲 + shader   │
│ 解析覆盖度 AA       │                   │ SDF / 羽化 AA       │
│ 效果 = 卷积核       │                   │ 效果 = fragment     │
│ 重采样 = CPU 采样器 │                   │ 重采样 = 纹理采样器 │
└─────────────────────┘                   └─────────────────────┘
        │                                           │
        └─────────────────────┬─────────────────────┘
                              ▼
                    ┌──────────────────┐
                    │ PresentTarget    │
                    │ Wayland / X11 /  │
                    │ Windows / 离屏    │
                    └──────────────────┘
```

### 3.1 一个具体的接口

```rust
/// 后端只做两件事：消费批次、产出像素。
/// Backends do two things: consume batches, produce pixels.
pub trait RenderBackend {
    type Target;

    /// 每批一次：后端自行决定实例化还是光栅化。
    /// Once per batch: the backend chooses instancing or rasterization.
    fn draw_batch(
        &mut self,
        target: &mut Self::Target,
        prims: &Primitives,
        batch: &Batch,
        clip: ClipId,
    ) -> Result<()>;

    /// 效果执行：只实现 pixel kernel，其余由上层的 EffectScheduler 决策。
    /// Effects: implement only the pixel kernel; scheduling is shared.
    fn cook(&mut self, src: &Self::Target, dst: &mut Self::Target, effect: &EffectPlan) -> Result<()>;

    fn capabilities(&self) -> BackendCaps;
}
```

**注意 `draw_batch` 的签名**：它收的是 `Primitives` **和** `Batch`（一段 range + kind），
不是一条一条的命令。这就是"批量"成为结构性保证的方式——后端**没有办法**逐条处理。

### 3.2 语义共享、实现分开的三处

| 能力 | 共享什么 | 各自实现什么 | 一致性保证 |
|---|---|---|---|
| **采样** | `Sampling` 枚举 + 取样几何规则（`floor(display→native)`） | CPU 逐像素取样 / GPU 纹理采样器 | 2×2 棋盘各倍率逐像素相等（无插值差异，采样方式相同） |
| **模糊** | `pad = ⌈3σ⌉`、可分离核、线性光域 | CPU 两趟卷积 / GPU 两趟 fragment | 同一输入，PSNR > 45dB（不是逐像素，见 §4.3 `[未证实]` 标注） |
| **分组不透明度** | `Layer` 语义（先合成再整体乘） | CPU 临时缓冲 / GPU 离屏纹理 | 两个半透明白块叠灰底，逐像素相差 < 2/255 |

---

### 3.3 存储域与运算域的分离（消除 SDR 的格式转换）

上一版曾写"SDR 也要在 f16 渲染再降 8-bit"——那是错的。**存储域可以就是 `Srgb8`**，
只要运算时用 LUT 往返线性化（详见 [`hdr-color-management.md`](hdr-color-management.md) §5.3）：

| | CPU | GPU |
|---|---|---|
| 存储 | `Srgb8` 缓冲 | `SRGB8_ALPHA8` 纹理 |
| 线性化 | 逐操作查表（寄存器内） | **硬件采样时自动** |
| 额外全屏 pass | **无** | **无** |

实测量化误差：10 层叠加 0 LSB，50 层 2 LSB——远小于 §2.2 的 2/255 容差。

### 3.4 CPU 光栅核心的选型（不沿用旧项目）

CPU 侧"路径 → 覆盖率"这一步用 **`zeno`**，不用旧项目的 tiny-skia。
详见 [`research/cpu-rasterizer-survey.md`](research/cpu-rasterizer-survey.md)：本机实测显示
**局部更新快 1.8×**（0.62 vs 1.14 µs/op），而局部更新正是 `Damage` 架构下的常态。

分工：`zeno` 只出 alpha 覆盖率，**合成/格式/效果/采样全在 `ui-paint`**——
这保证两条路径共享同一份混合语义。

## 4. 性能预算：两条路各自该快在哪

### 4.1 明确的分工

| 场景 | 首选路径 | 理由 |
|---|---|---|
| 4K 全屏覆盖层 + 效果链 | **GPU** | CPU 每帧写 ~33M 像素不可能做到 60fps |
| 小区域更新（拖一个滑块） | 两者都行 | `Damage` 只脏几十×几百像素，CPU 光栅更快（无 GPU 提交开销） |
| 无 GPU 机器 | **CPU** | 这是 CPU 路径存在的第一理由 |
| 离线导出（PNG/视频帧） | **CPU** | 确定性输出，不需要窗口 |
| 贴图编辑（`Canvas` 重采样） | 取决于尺寸 | 小画布 CPU，大画布 GPU |
| 测试 / CI | **CPU** | 无 GPU、确定性、可逐像素比对 |

**关键洞察**：**CPU 路径不是"降级路径"，而是"不同预算下的正确选择"。**
旧项目把 CPU 定位成"无 GPU 时的回退"，那是次优的——它让 CPU 路径长期不被优化。

### 4.2 性能预算（目标值，需实测校准）

| 指标 | CPU | GPU |
|---|---|---|
| 全屏重绘 4K | 不允许（>100ms） | < 8ms |
| 区域重绘 512×512 | < 4ms | < 2ms（含提交开销） |
| 单批 1000 个矩形 | < 2ms | < 0.3ms |
| 帧内 CPU 后端分配 | 0（复用缓冲） | 0（复用实例缓冲） |

### 4.3 这些数字的性质

**这是预算而非承诺**——写进设计是为了让"性能回归"有判据，不是为了现在就能保证。
实现后必须实测填入真实值。GPU 模糊与 CPU 模糊的 PSNR 目标（45dB）同样是待验证值。

## 5. 为什么另一种切法会失败

### 5.1 反例 A：两条独立实现（各写一套完整的渲染器）

成本翻倍，且**必然漂移**：同一个圆角矩形的观感会在两次独立实现里分叉，
调试时无法判断"是设计的观感就是这样"还是"某个后端有 bug"。

### 5.2 反例 B：GPU 优先，CPU 只做"能出图就行"

这是旧项目的实际路线（CPU 是 fallback）。后果：CPU 路径长期不被优化，
一旦 GPU 路径出问题（驱动 bug、HDR 目标不被支持），用户体验断崖式下降。

### 5.3 反例 C：共享三角形（让 CPU 和 GPU 吃同一份顶点）

技术可行（egui 就是这样），但要求 GPU 放弃实例化与 SDF——
在 4K 全屏场景下把 GPU 拉到与 CPU 同一水平线。

### 5.4 反例 D：共享光栅结果（CPU 渲染后上传纹理给 GPU）

看起来最省事，实则灾难：每帧上传 4K 纹理 = 33MB/帧 ≈ 2GB/s @60fps，
远超带宽预算，且失去 GPU 全部优势。

## 6. 这套设计的代价（诚实清单）

| 代价 | 影响 | 缓解 |
|---|---|---|
| 两条后端都要维护 | 每加一种图元要写两次 | 图元种类**刻意限制**为 7 种（§6.2）；新增图元的代价在 review 时显式评估 |
| AA 不可能完全一致 | 两后端边缘像素差 1–3/255 | 用 §2.2 的四条不变量替代逐像素相等 |
| 效果要写两份 | 每个内置效果两套实现 | `cook_cpu` 必需、`cook_gpu` 可选（§8.5 的 `CpuThenUpload` 兜底） |
| 测试要跑两遍 | CI 时间 | CPU 路径跑全量；GPU 路径只在有设备的机器上跑，降级为可选 job |
| 性能预算需实测 | 设计阶段无法保证 | 每条预算配一个 benchmark，回归即报警 |

## 8. 一个简化建议

**先只实现 CPU 路径，把 GPU 路径作为第二个后端接入。**

理由：

1. CPU 路径能保证 `window_hello` / `canvas_zoom` / `effects_zoo` 三个 example 在**任何机器**
   上跑通，不依赖 GPU 驱动；
2. 双后端一致性测试需要"参考实现"——CPU 是天然的确定性参考（无驱动差异）；
3. 先有 CPU 路径，`RenderBackend` trait 的形状会被真实需求打磨过一遍，
   再接 GPU 时不会因为要迁就 GPU 特性而改公共接口。

**这与"两条路都要性能良好"不矛盾**：优化是路径实现内部的事，接口只需一次设计对。
