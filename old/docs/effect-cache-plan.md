# 效果缓存：将我们的方案存档为将来计划

> 状态：**已实现 → 已搁置（2026-10-27 用户决定）**。本文记录「能不能做、前提是什么、
> 哪里会错」，以及我们实际实现过什么、为什么撤掉、撤销后留下的可复用结论。
> 当前代码走的是**成熟项目的做法**：每帧全量重算阶段，不做跨帧像素复用（见 §7）。
> 目标读者是将来动手的人，因此写清「为什么」而不是「怎么做」。

## 1. 问题

效果（模糊等）是逐像素的全区域运算。层是 1272×1397 时一次半径 6 的高斯模糊约
26 次纹理取样/像素，合计约 4600 万次取样/帧。而实际变化往往只有几十×几十像素。

要问的是：**能不能只重算变化影响到的部分，其余沿用上一次的输出。**

## 2. 结论先行

| 问题 | 结论 |
|---|---|
| 是否可行 | 可行，且当前「核 + 矩阵」的代数天然满足前提 |
| 最大前提 | 效果输出必须是**每层一张持久纹理**；现在它是乒乓 scratch，会被下一次覆盖 |
| 第二前提 | GPU 渲染器现在**完全没有 damage**（`Damage` 在 `ui-paint-gpu` 中 0 处引用），必须先把脏区接进来 |
| 缓存在哪一层 | **只能缓存在效果链的输出**，不能缓存在两趟之间 |
| 网格对齐是不是正确性要求 | **不是**。正确性只要求「重算 `D ⊕ reach`」；网格对齐是让复用能以整块瓦片寻址的**优化** |
| 脏区传播 | 两趟宽度不同：横向写 `D ⊕ (r, 2r)`，纵向写 `D ⊕ (r, r)` |
| 值得做的条件 | 脏区膨胀后远小于层，且效果趟本身不便宜 |

## 3. 为什么「缓存在链输出」而不是「趟之间」

中间结果是 RGBA8。若在第 1 趟之后缓存，第 2 趟读到的就是**已被量化过一次**的数据；
而重算路径不会。缓存命中与重算必须**逐位相同**，否则缓存会静默改变输出。

所以：

- 缓存在链的输出 → 输入相同时 GPU 确定性保证逐位相同 → 安全；
- 缓存在趟之间 → 需要把中间结果升到 RGBA16F 才安全，显存翻倍，是另一个量级的改动。

这条是「只能应用于逐像素算法一致的效果」的具体含义。

## 4. 脏区传播的准确宽度

设脏区 `D`（设备像素），核半径 `r`，效果链只有一次可分离模糊。

- 输出变化范围：`B = D ⊕ (r, r)`（两个方向都要膨胀，因为输出像素的邻域被触及）
- 纵向趟只需写 `B`；它读取横向趟的输出 `C = B ⊕ (0, r) = D ⊕ (r, 2r)`
- 横向趟只需写 `C`；它读取输入 `C ⊕ (r, 0)` —— 输入是层内容，本来就完整，不必裁剪

因此：

```
h_write = D ⊕ (r, 2r)
v_write = D ⊕ (r, r)
```

把两者都写成 `D ⊕ 2r` 也能跑对，但多做约一倍的活；写成 `D ⊕ r` 则**会错**（纵向趟读到
未更新的横向结果）。

多条效果串联时，从链尾往链头依次膨胀，每条效果的 `r` 累加。

> **2026-10-27 更正**（实测得到，本节原文只覆盖「一趟可分离模糊 = h+v」，`box_blur` 实际是
> 3 箱 = **六趟** h,v,h,v,h,v）。当时按「每个轴共用一条带」实现，边缘显出上一帧的内容：
> 第 k 趟读的是第 k+1 趟写过的带子**沿第 k+1 趟自身的轴**外扩一个 `r`，所以带子必须从输出
> **逐趟反向增长**，两轴的宽度在交替中各不相同，不能按轴合并。`r=1`、`D=(0,0,10,10)` 的六条带：
>
> ```
> (-2,-3,14,16) (-2,-2,14,14) (-1,-2,12,14) (-1,-1,12,12) (0,-1,10,12) (0,0,10,10)
> ```
>
> 该包含性当时由单元测试 `each_pass_band_contains_what_the_next_pass_reads` 钉住（改成按
> `k % 2` 分轴立即变红）。随 §11 一并撤下，将来重建时必须复用这条证明。

## 5. 网格对齐到底约束了什么

用户提出的判据是「效果区域顶点坐标在两个方向上的变化量对采样范围取模为 0」。

拆开看有两件事：

1. **正确性**：与网格无关。卷积是平移不变的；只要重算 `D ⊕ r`，任意整数位移都正确。
   唯一例外是**层尺寸变化**——`CLAMP_TO_EDGE` 的钳制位置变了，靠近边缘的缓存值会错。
   所以尺寸变化必须让边缘带（乃至整层）失效。
2. **可寻址性**：若缓存按瓦片组织，瓦片尺寸取 `r`，则区域位移为 `r` 的整数倍时，
   失效区恰好落在瓦片边界上，可以用整块瓦片表达「保留/重算」；非整数倍时只能表达成
   任意矩形，仍然正确，但多算一点。

所以判据的正确表述是：**网格对齐是让失效集能以整瓦片表达的充分条件，不是缓存正确的前提。**

## 6. 抽象放在哪

| 层 | 放什么 | 为什么 |
|---|---|---|
| `ui_core::effect` | `CachePlan::compute(dirty, reach, layer, grid) -> CachePlan { h_write, v_write, tiles_keep, bail }` | 纯数学、无 GPU、可单元测试。这块最容易算错，也最便宜去测 |
| 各后端渲染器 | 每层一张持久输出纹理、缓存键（链哈希 + 层矩形 + 网格相位）、按 `CachePlan` 设 scissor | 纹理生命周期与 GL/CPU 相关，无法移植 |

把「算什么」和「怎么存」分开，是因为前者能被测试钉住，后者只能靠真机验证。

## 7. 何时不该用

- 脏区膨胀后超过层的约 40%：全量更快，省掉判定的开销。
- 效果参数变化、层尺寸变化、链哈希变化：整层失效。
- `reach == 0` 的纯颜色效果：本来就是一趟全屏，缓存收益接近零。
- 每帧全量动画：脏区即全层，必然走全量分支。

## 8. 风险清单

| 风险 | 说明 |
|---|---|
| 双量化 | 已排除：只在链输出缓存 |
| 尺寸变化 | `CLAMP_TO_EDGE` 位置改变，边缘带失效；尺寸变了基本等于整层失效 |
| 嵌套层 | 子层输出是父层输入，脏区必须从子层向外传播（子层 `D` 膨胀后并入父层 `D`） |
| 单位 | 现有 damage 是**逻辑单位、帧级**；缓存需要**设备像素、按层归属**。转换点必须唯一，否则重演「逻辑/设备求交只在 scale=1 成立」那类错误 |
| 显存 | 每层 +1 张持久纹理。层数 = 嵌套深度，通常 ≤ 3，可接受 |
| 缓存与乒乓共用缓冲 | 现在 `effect_scratch[2]` 就是乒乓；缓存必须独立，否则下一帧就被覆盖 |

## 9. 建议的落地顺序

1. **GPU 接上 `Damage`**（当前 0 处引用）。先只用于整帧 scissor，建立通路与测试。
2. **效果输出独立成每层一张持久纹理**，乒乓只留作中间缓冲。这一步不改行为，纯结构。
3. **`CachePlan` + 单元测试**：先写测试（`D ⊕ (r,2r)` / `D ⊕ (r,r)`、多效果累加、尺寸变化失效、
   网格相位判定），再写实现。
4. **GPU 按 `CachePlan` 裁剪两趟**；CPU 侧同构（`render_region` 已存在）。
5. 最后再谈「层内容增量重绘」——那是几何绘制的脏区问题，与效果缓存正交，
   但两者共用同一套 damage 通路，先做第 1 步不会白费。

## 10. 量级估计

层 1272×1397 ≈ 1.78 M 像素，半径 6 模糊 26 次取样/像素 ≈ 4600 万次/帧。
一次文本编辑的脏区约 200×40，膨胀后约 (200+12)×(40+24) ≈ 1.35 万像素
→ 约 35 万次取样，**约 130 倍**。合成那一步仍是全屏（每像素 1 次取样），可以顺带裁到脏区。

结论：收益主要来自效果趟，与几何绘制量无关；这也是为什么它值得做，但**必须先把
持久输出纹理与 damage 通路铺好**。

## 11. 已实现过什么，为什么撤掉（2026-10-27）

我们实现过一整套跨帧复用，共六处相互纠缠的记账：

| # | 机制 | 位置 | 作用 |
|---|---|---|---|
| 1 | 帧缓冲保留 + 逐脏矩形清空 | `ui-paint-gpu/renderer.rs` | 不清全帧，只清 app 报的脏区 |
| 2 | `raw` 快照 + `raw_valid` + `frost::ring` | 同上 | 未模糊背景的跨帧缓存 |
| 3 | `backdrop_is_dirty` 探针 | 同上 | 干净磨砂跳过重算，防二次模糊 |
| 4 | `frost::split` 子块重算 | 同上 + `ui-core/frost.rs` | 只重算磨砂内变化部分 |
| 5 | `CachePlan::compute` + `pass_bands` | `ui-core/effect.rs` | 每趟写区的嵌套带契约 |
| 6 | CPU `previous` 拷贝 + 区域重绘 | `ui-paint/lib.rs` | 上帧像素保留 |

代价：修一个洞开一个洞。按因果链列出的实际 bug——读取距离与工带混淆、blit 静默失败、
就地递归、整帧快照二次模糊、frost 携带黑带、拖尾排空、written 少报、alpha=0 快照、
`raw_valid` 陈旧、清空面积≠重写面积、**每轴共用一条带**（原则性根因）、
CPU 把直通缓冲按预乘读。最后一条与第一条同源：**契约越复杂，静默错误的种类越多**。

成熟项目的选择与此相反：Flutter 每帧重建全部 `Layer`；Skia 只缓存**渲染结果**
（`SkImageFilter` 的 cache 键含源矩形），不缓存中间像素；Haze 按阶段失效整层重算
（ADR-0002/0003）。它们宁可重算，也不让「谁写过哪块」决定画面。

撤掉后的契约（写进代码注释）：

- **每个阶段每帧从当帧真实场景整帧重算**，输入不来自任何跨帧缓存；
- 帧缓冲每帧清空后重绘，不再依赖上一帧内容；
- `Damage` 只用于**提交**（dmabuf damage 给合成器）与绘制裁剪，不用于决定是否重算；
- 因此不再有「边缘显示旧内容」「面板慢慢向背景靠拢」这类残留：它们的前提是复用。

将来若要重新启用，本节六处按依赖顺序重建即可；§5 的「缓存键含输出矩形/源矩形」是硬前提，
`pass_bands` 的嵌套包含性证明（r=1、D=(0,0,10,10) → 六条带逐条外扩）仍然成立且值得复用。
